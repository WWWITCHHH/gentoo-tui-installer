# Архитектура

## Цели и ограничения

Установщик — набор Bash-модулей, рассчитанный на запуск из Gentoo Minimal
Installation CD. Основные ограничения, определившие архитектуру:

- нет гарантированной установки `dialog`/`whiptail`, поэтому TUI написан на
  ANSI-последовательностях;
- live-среда должна оставаться работоспособной при ошибках и повторных запусках;
- нельзя сохранять пароли в конфигурации, состоянии или журналах;
- destructive-операции должны быть явно подтверждены;
- установка должна продолжаться с последнего завершённого этапа;
- поддерживается только amd64 и только GRUB.

Bash выбран как компромисс: он гарантированно есть в Minimal CD, не требует
сборки и позволяет напрямую вызывать системные утилиты. Цена — необходимость
дисциплины в quoting, тестировании и разборе ошибок.

## Структура проекта

```text
gentoo-installer          точка входа, выбор версии, загрузка модулей
VERSION                   версия релиза
lib/
  core.sh                 константы, журнал, конфигурация, состояние, helpers
  validate.sh             валидаторы и config_validate
  ui.sh                   ANSI TUI, меню, ввод, подтверждения
  ui-run.sh               запуск команд, журналы, загрузки, интерактив
  preflight.sh            проверки live-среды
  disks.sh                обнаружение дисков, план, разметка, UUID, mount
  stage3.sh               latest-stage3, SHA256/GPG, распаковка
  portage.sh              chroot, make.conf, sync, профиль
  kernel.sh               firmware, microcode, ядро, initramfs
  system.sh               hostname, время, locale, fstab, пользователи
  tools.sh                сеть, службы, sudo, gentoolkit
  bootloader.sh           GRUB UEFI/BIOS и проверка grub.cfg
  finalize.sh             depclean, очистка, размонтирование
  wizard.sh               интерактивные меню и редактирование конфигурации
  main.sh                 CLI, preflight-поток, оркестрация этапов
conf/installer.conf.example
tests/                    unit-тесты без root и блочных устройств
docs/                     документация
```

Загрузка модулей плоская: точка входа подключает все файлы через `source`.
Функции не изолированы в namespace, поэтому имена имеют префиксы (`disk_`,
`stage3_`, `kernel_`, `wizard_`, `ui_` и т. д.), а глобальные переменные —
префиксы `GI_`, `CFG_`, `PLAN_`, `STATE_`, `UI_`.

## Слои

```text
                     gentoo-installer
                            │
          ┌─────────────────┼──────────────────┐
          │                 │                  │
        main.sh          wizard.sh          preflight.sh
          │                 │                  │
          └──────────────┬──┴──────────────────┘
                         │
        ┌────────────────┼─────────────────┐
        │                │                 │
      disks.sh        stage3.sh         portage.sh
        │                │                 │
        └────────────────┼─────────────────┘
                         │
      kernel.sh   system.sh   tools.sh   bootloader.sh   finalize.sh
                         │
                 core.sh  validate.sh  ui.sh  ui-run.sh
```

`core.sh` не зависит от предметных модулей. `wizard.sh` и `main.sh` — верхний
слой, который связывает этапы. `finalize.sh` вызывает helpers из `disks.sh` и
`portage.sh`; это осознанная связка, а не циклическая зависимость.

## Поток выполнения

```text
main()
 ├─ разбор CLI
 ├─ проверка TTY и root
 ├─ init_workdir()             /var/lib/gentoo-installer, lock, журнал
 ├─ config_defaults()
 ├─ config_load()               если файл существует
 ├─ config_derived()
 ├─ state_load()
 ├─ trap INT/TERM/HUP
 ├─ ui_init()
 ├─ banner
 ├─ --resume? ── да → main_start_installation()
 └─ нет → главное меню мастера
             └─ «Начать / продолжить»
                  └─ main_start_installation()
                       ├─ предупреждение (только для новой установки)
                       ├─ preflight_run()
                       ├─ выбор диска или ручное назначение разделов
                       ├─ config_derived()
                       ├─ config_validate()
                       ├─ config_save()
                       └─ installation_run()
```

`installation_run()` сначала проверяет, завершён ли этап `disk`. Если да, он
монтирует целевые ФС по сохранённым UUID. Затем последовательно вызывает
`step_<name>` для всех этапов из `STATE_STEPS`:

```text
disk → stage3 → portage → kernel → system → tools → bootloader → finalize
```

После успешного шага вызывается `state_mark_done`, который сразу пишет файл
состояния. При ошибке шаг не отмечается, установщик показывает диалог и
возвращается в меню. Пользователь может исправить проблему, повторить команду
или запустить установку снова.

## Состояние и возобновление

`STATE_STEPS` — единственный источник порядка этапов. Файл состояния содержит
только строки `step=done`; неизвестные и повреждённые строки игнорируются.
Запись атомарная: временный файл, `chmod 0600`, `mv`.

Свойства модели:

- этап считается завершённым только после успешного возврата функции;
- завершённые этапы при повторном запуске пропускаются;
- незавершённый этап выполняется заново целиком;
- отката изменений нет;
- `disk` — единственный этап, который при возобновлении требует специального
  восстановления: `disks_mount_all` проверяет UUID и точки монтирования;
- `finalize=done` — терминальное состояние; `--resume` завершается успешно, а
  мастер предлагает сбросить состояние для новой установки.

Состояние не является транзакцией. Если команда внутри шага выполнилась, но шаг
упал позже, при повторе команда может выполниться ещё раз. Поэтому команды
выбираются идемпотентными там, где это возможно; разметка и форматирование
идемпотентными не являются и защищены отдельными подтверждениями.

## Конфигурация

Конфигурация — не shell-файл. `config_load` разбирает строки регулярным
выражением, проверяет ключ по списку `CONFIG_KEYS` и присваивает `CFG_<KEY>`.
Значения не подвергаются подстановке. Это устраняет целый класс атак через
конфигурационный файл и делает формат предсказуемым.

`config_defaults` задаёт встроенные значения. `config_derived` вычисляет
зависимые поля (`CFG_INIT`, профиль, очистка неиспользуемых разделов и UUID).
`config_save` записывает все ключи, включая пустые, с экранированием `"` и `\`.
Файл создаётся атомарно с правами `0600`.

Пароли не входят в `CONFIG_KEYS`. Они запрашиваются через `ui_password_twice`,
хранятся только в локальной переменной и `UI_SECRET`, передаются в `chpasswd`
через stdin и очищаются сразу после использования. `ui_run_input` не пишет
входные данные в журнал.

## TUI

`ui.sh` реализует:

- цвета только при TTY и при отсутствии `NO_COLOR`;
- рамки, прогресс-бар, перенос текста;
- меню с тегами и описаниями, навигацию стрелками, Home/End, цифрами и `q`;
- ввод строк с редактированием, Backspace, Ctrl-U, Ctrl-W;
- ввод целых чисел с диапазоном;
- подтверждение yes/no;
- ввод пароля с двумя попытками;
- отображение файла и длинного текста.

Ключевая деталь: `wizard_bool` вызывает `ui_confirm` с перенаправлением вывода
TUI в stderr, а в stdout печатает только `yes` или `no`. Иначе command
substitution захватил бы ANSI-последовательности и записал их в конфигурацию.
Это поведение закреплено тестом `test_wizard.sh`.

Стандартный поток TUI — stdout. Для command substitution, которая должна
получить чистое значение, используется явное перенаправление. Это правило
важно сохранять при добавлении новых функций.

## Выполнение команд и ошибки

`ui_run` — основной способ запуска внешних команд:

1. создаёт отдельный журнал `NN-step.log` с правами `0600`;
2. печатает команду в журнал;
3. запускает её в фоне с stdin из `/dev/null`;
4. показывает spinner и последнюю строку журнала;
5. при ошибке предлагает `R` — повторить, `L` — открыть журнал, `A`/Esc —
   прервать.

`ui_run_input` используется для команд, которым нужен stdin (например,
`chpasswd`). Вход не логируется. `ui_interactive` отдаёт управление
`/dev/tty` для `cfdisk` и `make menuconfig`.

`die` пишет ошибку в журнал, очищает экран и завершает процесс. `must` — обёртка
для команд, где ошибка должна быть фатальной. Модули стараются возвращать
ненулевой код и показывать `ui_error`, чтобы мастер мог продолжить работу.

## Диски

`disks.sh` строит план в параллельных массивах:

```text
PLAN_NUM[]     номер раздела
PLAN_ROLE[]    esp | boot | swap | root | home
PLAN_SIZE[]    размер в MiB
PLAN_START[]   начало в MiB
PLAN_END[]     конец (исключающий) в MiB
PLAN_FSTYPE[]  vfat | xfs | ext4 | btrfs | swap
PLAN_MOUNT[]   /efi | /boot | none | / | /home
PLAN_LABEL[]   метка раздела
```

`_plan_add` проверяет положительный размер, отсутствие перекрытий и выход за
диск. Последний MiB диска не используется, чтобы избежать проблем с
выравниванием и GPT backup header.

Автоматическая схема:

- UEFI: ESP 1024 MiB + swap? + root + `/home`?;
- BIOS: `/boot` 1024 MiB + swap? + root + `/home`?;
- root получает остаток; при отдельном `/home` его начало вычисляется от конца
  диска, а root — оставшееся пространство между fixed-разделами и `/home`.

Проверки до разметки: диск существует и является целым блочным устройством, на
нём нет смонтированных разделов и активного swap, BIOS-диск не больше 2 TiB.

После `parted`, `partprobe` и `udevadm settle` установщик ждёт появления
разделов (до 20 секунд), форматирует их, снимает UUID через `blkid` и монтирует
по UUID. `mount_by_uuid` идемпотентен: если точка уже смонтирована с нужным
UUID, повторное монтирование не выполняется.

Ручная схема не создаёт таблицу разделов автоматически. Можно открыть `cfdisk`,
затем назначить роли. Проверяются существование разделов, уникальность,
принадлежность одному диску и тип таблицы (GPT/MBR). `FORMAT_*` позволяют
сохранить существующие ФС.

`disks_unmount_all` сначала выключает swap, затем рекурсивно размонтирует
`$GI_ROOT` (вместе с вложенными `/efi`, `/boot`, `/home`). Перед этим всегда
вызывается `chroot_unmount`, чтобы снять `/proc`, `/sys`, `/dev`, `/run`.

## Chroot

`chroot_mount` монтирует:

```text
/proc  proc
/sys   --rbind + --make-rslave
/dev   --rbind + --make-rslave
/run   --bind + --make-slave
```

`chroot_unmount` снимает их в обратном порядке через `umount -R`. Каждый
предметный этап (Portage, ядро, система, службы, загрузчик, завершение)
вызывает `chroot_mount` самостоятельно. Это делает этапы независимыми и
позволяет возобновить установку с любого из них. Если этап падает, монтирования
остаются; следующий запуск либо переиспользует их, либо снимет перед повторной
разметкой/сбросом.

## Загрузка и проверка Stage3

`stage3_resolve` либо берёт `STAGE_URL`, либо скачивает `latest-stage3` и
разбирает строку формата:

```text
20261018T124555Z/stage3-amd64-openrc-20261018T124555Z.tar.xz 284788352
```

`ui_download` умеет докачивать файл через `curl -C -`, проверять ожидаемый
размер, обрабатывать уже полный файл и повторять загрузку без resume, если
сервер не поддерживает диапазоны.

Проверка:

- SHA256 sidecar (может быть PGP-clearsigned; берётся первая строка с 64 hex);
- GPG `.asc` ключом из `/usr/share/openpgp-keys/gentoo-release.asc`;
- если sidecar отсутствует, используется оставшийся способ;
- если нет ни одного способа — `die`.

Временный GNUPGHOME находится в рабочем каталоге с правами `0700`.

## Безопасность и границы доверия

- Конфигурация не исполняется как shell.
- Значения для `/etc/default/grub` и `make.conf` проходят quoting через
  `shell_quote`; kernel cmdline дополнительно запрещает `$`, `` ` ``, `\`,
  кавычки и переводы строк.
- Пароли не попадают в файлы и журналы; они передаются через stdin.
- Destructive-операции требуют `ERASE`, кроме явного `--yes`.
- Проверка окружения выполняется до первого изменения диска.
- Stage3 проверяется по SHA256 и, когда возможно, по GPG.
- Установщик доверяет live-среде Minimal CD и её инструментам; он не защищает
  от скомпрометированного установочного носителя или mirror.
- Secure Boot, шифрование и hardening не настраиваются.

## Тестовые хуки

Все пути можно переопределить через переменные окружения:

```text
GI_ROOT       целевая система (по умолчанию /mnt/gentoo)
GI_WORKDIR    рабочий каталог (по умолчанию /var/lib/gentoo-installer)
GI_CONFIG_FILE
GI_STATE_FILE
GI_LOG_DIR
GI_LOG_FILE
GI_DOWNLOAD_DIR
GI_GNUPG_HOME
```

`tests/run.sh` создаёт временный каталог и передаёт эти переменные каждому
тесту. Благодаря этому unit-тесты не требуют root, не пишут в `/var/lib` и не
трогают блочные устройства.

## Компромиссы

- **Bash вместо Python/Go.** Нет зависимостей в Minimal CD, но слабее типизация
  и больше quoting-рисков.
- **Плоское пространство имён.** Проще загрузка, но требуется дисциплина
  префиксов.
- **Последовательные этапы без транзакций.** Понятное возобновление, но
  повторный запуск может повторить команды.
- **Собственный TUI.** Нет внешних зависимостей, но ограниченная доступность и
  необходимость тестировать терминалы вручную.
- **Один диск и один загрузчик.** Меньше кода и рисков, но не покрывает LUKS,
  LVM, RAID, dual boot и Secure Boot.
